**What this proposes**
This design introduces a transactional synchronization layer across the NestJS backend and Next.js frontend of Debitinfo.GE so that every write operation immediately updates all dependent PostgreSQL tables and UI views. Specifically, registering or verifying debtors will atomically upsert `User`, `IndividualProfile`/`CompanyProfile`, `DebtClaim`, and cross-linked `StagedRegistryItem` records, while startup reconciliation will link orphaned debtor records to valid registered creditors. Payment confirmations and debt write-offs will idempotently update balances and statuses across both `DebtClaim` and `StagedRegistryItem` (along with `PaymentTransaction` and `RepaymentInstallment` records), and portfolio dispatch will route cases to lawyers (`LegalCase`), operators (`DebtClaim.assignedOperatorId`), and field officers (`FieldVisitTask`). Finally, all hardcoded rows, static KPI counters, mock document/installment fallbacks, and in-memory blog arrays across the frontend and Next.js API routes will be replaced with live database queries and `/api/v1/analyst/blog` persistence.

**How the existing system works, per this document**
Debitinfo.GE currently suffers from a split-brain architecture where analyst registration and verification workflows (`registerCreditor`, `addDebtorsToCreditor`, `verifyDebtor`) write only to the flat `StagedRegistryItem` table using fragile plain-text `creditorName` links, while operational portals (`/dashboard`, `/legal`, `/crm`, `/field-officer`, `/accountant`, `/analyst/analytics`) read from `User` and `DebtClaim`. Payment confirmations subtract from `DebtClaim.remainingAmount` without idempotency guards (allowing double deductions) and without updating `StagedRegistryItem.amount`, `RepaymentInstallment`, or `PaymentTransaction`, while write-offs similarly leave `StagedRegistryItem` stale. Portfolio dispatch (`dispatchTask`) only creates tasks for `FIELD_OFFICER` users and ignores `LEGAL` and `OPERATOR` assignments, and `getExcelDebtors` overwrites multi-claim debtors by indexing a `Map` solely by `debtorId`. On the frontend, multiple views (`CreditorDashboardView.tsx`, `DebtorDashboardView.tsx`, `crm/page.tsx`) and service/API route layers fall back to hardcoded debtor rows, static KPI counters, fake supporting documents/installment schedules, and in-memory blog posts (`INITIAL_BLOG_POSTS`).

Unified Registration and Verification Pipeline` ([full-stack-data-synchronization.md](file:///C:/Users/mike/Documents/debitinfo/docs/designs/full-stack-data-synchronization.md#L148-L152)), `### 3. * **Discrepancy Description & Rationale**:
  1. In `syncDebtorAndClaimFromStagedItem` (lines 149–151), the document states that the service "Upserts a `User` with `role: Role.DEBTOR` and the corresponding `IndividualProfile` ... or `CompanyProfile`", and later alludes in Alternative 2 (line 245, line 252) to unique constraints on `User.email` / `CompanyProfile.taxId` and "password hashing for new users".
